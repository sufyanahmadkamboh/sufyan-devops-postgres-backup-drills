# 5. Object storage (S3)

## What is it?

**Object storage** stores files ("objects") in **buckets** and is used over HTTP(S) with an API. **S3** is Amazon's object storage, and its API has become the standard: many products speak "S3-compatible" (SeaweedFS, Ceph, Garage, Cloudflare R2, Wasabi, Hetzner Object Storage...).

## Why this project uses it

Backups must live **somewhere else** than the database: another machine, ideally another building or region. Object storage is cheap, practically unlimited, very durable, and has features made for backups (versioning, object lock). pgBackRest writes to it natively.

The lab runs **SeaweedFS** in a container, so the whole project works offline and costs nothing. In production you change the endpoint to AWS S3 (or any S3-compatible service); nothing else changes.

**Why not MinIO?** For years MinIO was the default local S3. In 2025 it stopped publishing community binaries and container images, went into maintenance mode, and the repository was archived in 2026. A project that is supposed to be usable in production should not start on an abandoned component, so this one uses SeaweedFS, which is actively maintained.

**Alternatives:** Garage (small, single binary), Ceph RGW (large clusters), RustFS (newer), the cloud providers' own storage.

## How it works

### Buckets, objects, keys
- A **bucket** is a top-level container: here `pgbackrest`.
- An **object** is a file inside it, with a path-like name: `main/archive/main/18-1/.../000000010000000000000005-....zst`.
- Programs authenticate with an **access key** and a **secret key** (like a user name and password). Each key can be limited to certain buckets and actions.

### Path-style vs virtual-hosted URLs
AWS uses `https://bucket.s3.amazonaws.com/object` (virtual-hosted style). Local services usually need `https://s3:8443/bucket/object` (**path style**), hence `repo1-s3-uri-style=path`.

### HTTPS with a private CA
pgBackRest only talks to S3 over HTTPS and checks the certificate. In the lab, `scripts/setup.sh` creates a small **private certificate authority** and a certificate for the host name `s3`; pgBackRest trusts that CA through `repo1-storage-ca-file`.

## Where it is integrated

[`deploy/compose.yaml`](../deploy/compose.yaml):

```yaml
s3:
  networks: [storage]
  image: chrislusf/seaweedfs:4.48
  command:
    - server
    - -dir=/data
    - -master.telemetry=false
    - -s3
    - -s3.port=8333
    - -s3.port.https=8443
    - -s3.cert.file=/certs/s3.crt
    - -s3.key.file=/certs/s3.key
    - -s3.config=/run/secrets/s3_identities
```

`-s3.config` points to the access rules generated by [`scripts/setup.sh`](../scripts/setup.sh): one identity, `pgbackrest`, allowed to read, write, list and tag only the bucket `pgbackrest`:

```json
"actions": ["Read:pgbackrest", "Write:pgbackrest", "List:pgbackrest", "Tagging:pgbackrest"]
```

A one-shot `s3-init` service creates the bucket if it does not exist yet (`s3.bucket.create -name pgbackrest`).

### Moving to AWS S3 in production
Only the backup host's environment changes, for example:

```yaml
environment:
  S3_ENDPOINT: s3.eu-central-1.amazonaws.com
  S3_REGION: eu-central-1
  S3_URI_STYLE: host
```

plus real keys in the secrets (or an IAM role). Turn on bucket versioning or **Object Lock** so that even a stolen key cannot delete old backups.

## Try it

```bash
# the bucket's contents, as pgBackRest sees them
docker compose -f deploy/compose.yaml exec -u postgres backup pgbackrest --stanza=main repo-ls --recurse backup

# HTTPS health check, trusting the project CA
docker compose -f deploy/compose.yaml exec backup curl -s --cacert /etc/pgbackrest/tls/ca.crt https://s3:8443/healthz -o /dev/null -w '%{http_code}\n'

# without a key, the bucket is closed (expect 403)
docker compose -f deploy/compose.yaml exec backup curl -s --cacert /etc/pgbackrest/tls/ca.crt https://s3:8443/pgbackrest/ -o /dev/null -w '%{http_code}\n'
```

## Common mistakes

- **Storing backups on the same server or the same account as the database.** One incident takes both.
- **Disabling TLS checks** (`verify-tls=n`) "to make it work". Use a proper CA instead.
- **One key with full admin rights** for backups. Limit the key to one bucket.
- **No protection against deletion.** Ransomware deletes backups first. Use versioning/Object Lock and keep the key off the database host.

2. Why does the lab need `repo1-s3-uri-style=path`?
3. What would you change to move the repository to AWS S3?

<details><summary>Answers</summary>

1. A bucket is a named container; objects are the files stored inside it, each with a key (name).
